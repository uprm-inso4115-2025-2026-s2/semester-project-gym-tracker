== 1. Introduction to Conceptual Objects

A conceptual object:

- represents a system-specific concept
- contains identifiable instances
- shares common properties and behaviors
- may differ in internal state across instances

Conceptual object modeling helps engineers organize domain knowledge before implementation.

---

== 2. Types of Conceptual Objects

=== Entities

Entities are passive and autonomous objects that may exist independently.

Examples from real-world systems include:

- Library Book
- Customer Account
- Patient Record
- Vehicle

Characteristics:

- independently identifiable
- may exist without other objects
- contain attributes and properties

Example structure:

----
[Book]
- ISBN
- Title
- Author
- PublicationYear
----

---

=== Associations

Associations define conceptual links between objects.

Examples:

- Student enrolls in Course
- Customer places Order
- User borrows Book

Associations describe:

- connected objects
- participation roles
- multiplicity constraints

Example:

----
[Student] ---- EnrolledIn ---- [Course]
----

---

=== Agents

Agents are active conceptual objects capable of controlling behavior.

Examples:

- TrainController
- Payment Processor
- Notification Manager

Characteristics:

- active behavior
- autonomous actions
- system interaction control

---

=== Events

Events are instantaneous conceptual objects.

Examples:

- User Login
- Purchase Request
- Payment Confirmation

Characteristics:

- occur in a single state
- represent transitions or actions
- may trigger behaviors

---

== 3. Attributes and Multiplicity

Attributes represent intrinsic characteristics of conceptual objects.

Examples:

[cols="2,2", options="header"]
|===
| Object | Example Attributes

| Student
| ID, Name, GPA

| Product
| Name, Price, Quantity

| Reservation
| Date, Duration
|===

Attributes may include multiplicities.

Examples:

- `[1..1]` mandatory single value
- `[0..1]` optional value
- `[0..*]` multiple optional values

Example:

----
[Customer]
PhoneNumbers [0..*]
Email [1..1]
----

---

== 4. Specialization and Generalization

Specialization organizes concepts into subclasses.

Example:

----
[Vehicle]
   |
   +--> [Car]
   |
   +--> [Truck]
----

Inheritance allows specialized concepts to reuse shared features.

Benefits:

- avoids duplication
- improves maintainability
- increases abstraction quality

---

== 5. Aggregation and Composition

Aggregation models “whole-part” relationships between objects.

Example:

----
[Library]
   |
   +--> [Bookshelf]
          |
          +--> [Book]
----

Composition is a stronger relationship where components exist only with the parent object.

Examples:

- Order → Order Items
- Car → Engine
- House → Rooms

== 7. Modeling Heuristics

Important heuristics include:

- Determine whether a concept is an object or attribute
- Identify associations from domain relationships
- Distinguish entities, agents, associations, and events
- Apply specialization only when meaningful
- Use aggregation carefully
- Avoid poor modeling practices ("bad smells")

---

== 8. Common Modeling Mistakes

Poor conceptual models may include:

- implementation-oriented naming
- vague object definitions
- missing relationships
- unnecessary duplication
- treating relationships as attributes instead of associations

Example of bad practice:

----
Loan
BookID
BorrowerID
----

Better representation:

----
[Borrower]
      |
      +---- Loan ----+
                     |
                 [Book]
----


---

== 🧠 Key Insight

Conceptual object modeling improves Requirements Engineering because it transforms vague domain descriptions into structured system representations.

Instead of describing systems only through text, engineers can model entities, relationships, constraints, and abstractions visually and systematically.

This reduces ambiguity, improves communication, and creates a stronger foundation for later system design.
