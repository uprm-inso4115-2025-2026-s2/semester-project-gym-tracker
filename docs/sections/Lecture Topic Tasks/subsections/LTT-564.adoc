= Requirements Evolution Log — Documenting Requirement Changes
:toc:
:toclevels: 2

== Overview

This document presents a formal Requirements Evolution Log for the Gym Tracker application,
covering the full project lifecycle from Milestone 1 through Milestone 3. It traces how key
requirements across the system's major subsystems were added, modified, deleted, or replaced
as the project progressed. For each change, the triggering cause and downstream impact are
documented. This serves as a post-project traceability and retrospective artifact applying
Requirements Evolution techniques (Lecture 15, RE Chapter 6).

=== Description

The evolution process followed a natural lifecycle across the three milestones:

- *Milestone 1*: Initial domain exploration established the first set of requirements
  through stakeholder identification, domain acquisition, and concept formation.
- *Milestone 2*: Feature development surfaced implementation constraints, inconsistencies,
  and new stakeholder perspectives that drove requirement modifications.
- *Milestone 3*: Finalization led to scope adjustments, deprecation of infeasible requirements,
  and replacement of under-specified ones with refined versions.

---

== Change Type Classification

[cols="1,3", options="header"]
|===
| Change Type | Definition

| Addition
| A new requirement was introduced that did not exist in the prior milestone.

| Modification
| An existing requirement was altered in scope, detail, priority, or phrasing.

| Deletion
| A requirement was dropped or permanently deferred from the system scope.

| Replacement
| A requirement was superseded by a more refined or restructured version.
|===

---

== Evolution Trigger Classification

[cols="1,3", options="header"]
|===
| Trigger Category | Description

| Domain Refinement
| A change in the domain model, domain attributes, or concept formation revealed that the requirement needed updating.

| Stakeholder Input
| New or revised stakeholder perspectives (personas, agents, goals) caused a requirement to be added or changed.

| Implementation Constraint
| A technical or architectural limitation discovered during development forced a requirement change.

| Inconsistency Resolution
| A conflict or contradiction between requirements or domain artifacts was resolved by updating one or more requirements.

| Scope Adjustment
| A deliberate decision to expand or narrow the system scope across milestones affected one or more requirements.
|===

== Key Observations

- *Modifications* were the dominant change type (11 of 15), reflecting a project that
  iteratively refined requirements rather than radically restructuring them.

- *The Notification subsystem* had the highest requirement volatility (7 changes),
  consistent with its role as a cross-cutting concern dependent on multiple other modules.

- *The single Deletion* (Issue #451 — Membership subsystem) represents a deliberate
  scope consolidation decision made during Milestone 3 closure.

- *Implementation Constraints* were a notable trigger in Milestone 2 → 3 transitions,
  particularly for notification timing and frequency behaviors discovered during development.

- *No requirements were added after Milestone 2*, confirming that the project entered
  a stabilization and formalization phase during Milestone 3.
