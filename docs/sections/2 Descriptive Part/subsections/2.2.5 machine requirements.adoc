==== 2.2.5 Machine Requirements

===== Definition and Status

Machine requirements describe measurable, verifiable quality attributes the system-to-be must satisfy (e.g., performance, scalability, availability, security, and maintainability). They constrain how well the fitness-tracking web application (React + Supabase) must behave under expected and stressed operating conditions.

These requirements are still under development. Some thresholds will be refined as the team gathers usage expectations and runs basic load and reliability checks.

===== Machine Requirements

====== Interactive Response Time (Performance)

[.changed]#For authenticated Users, the system shall meet the following response-time targets under normal load:#

* [.changed]#In-application interactions (navigating dashboard views, updating UI state after data fetch) shall be complete within ≤ 500 ms for at least 95% of requests.#

* [.changed]#Server-backed operations (e.g., creating/editing Workout Sessions, updating Goals) shall complete with a server-acknowledged result within ≤ 1.0 second for at least 95% of requests.#

* [.changed]#Initial page load or heavy operations (first dashboard load after login) shall be complete within ≤ 2.0 seconds for at least 95% of requests.#

“Server-acknowledged result” means the data is successfully written [.changed]#to or# read from persistent storage and [.changed]#confirmation is returned to# the client.

====== Concurrent Usage Target (Scalability)

[.changed]#The system shall support at least 100 concurrent active sessions performing typical actions (viewing dashboard, logging workouts, editing workouts, updating goals) without violating Initial Page Load Time response-time targets.#

* [.changed]#“Concurrent” refers to overlapping GymGoer activity within a time window.#

[.changed]#Under load exceeding 100 concurrent active sessions:#

* [.changed]#The system shall continue operating without data loss or service unavailability.#

* [.changed]#The system may degrade gracefully as follows:#

** [.changed]#Response times may increase but shall remain ≤ 2.5 seconds for at least 90% of requests.#

** [.changed]#The system shall not allow indefinite delays or request starvation for any active GymGoer.#

** [.changed]#The system shall provide GymGoer-facing feedback (“High system load—responses may be slower than usual”) when performance degradation is detected.#

====== Availability (Reliability/Availability)

[.changed]#The system shall achieve at least 99.9% monthly availability for core features:#

* [.changed]#authentication#

* [.changed]#viewing dashboard#

* [.changed]#creating/editing workouts#

* [.changed]#creating/updating goals#.

[.changed]#The system shall be designed to minimize or eliminate downtime during updates through techniques such as:#

* [.changed]#Rolling deployments#

* [.changed]#Hot standby#

[.changed]#If schedule maintenance is unavoidable, it shall be rare, justified and communicated to GymGoers at least 24 hours in advance.#

====== Data Durability on Failure (Reliability)

When a write operation (e.g., logging a Workout Session or updating a Goal) returns success to the client, the system shall persist the change such that it remains retrievable after client refresh or reconnect. The system shall not acknowledge success unless the data is committed to persistent storage.

[.added]#Satisfiability and Feasibility Discussion#
[.added]#Satisfiability: This requirement is satisfiable within the current design because the machine requirements already define success in terms of committed persistent storage rather than temporary UI acknowledgment, and the interface requirements now state that the system must not report success before backend confirmation. The risk assessment further supports this requirement by identifying failed workout persistence as a concrete failure mode and proposing countermeasures such as retry logic, temporary local caching, and explicit success/failure feedback. Together, these sections provide a coherent basis for satisfying durability expectations.#

[.changed]#Feasibility: This requirement is feasible within project constraints because the selected backend platform is a managed persistence service and the document does not require custom distributed-storage research or unusually strict fault-tolerance guarantees beyond normal web reliability practice. The requirement is stronger than simple best-effort saving, but it remains realistic: the team can implement it through confirmed writes, controlled GymGoer feedback, and retry-oriented resilience behavior already described elsewhere in the document.#

====== Authentication and Session Security (Security)

The system shall require authentication for all access to [.changed]#GymGoer#-specific data. The system shall ensure that a [.changed]#GymGoer# can only read or modify their own Workout Sessions, Goals, and Progress History via enforced authorization checks.

The session timeout / token lifetime policy will be determined based on Supabase defaults and course security expectations.

====== Protection of Data in Transit and at Rest (Security/Privacy)

The system shall protect data in transit using HTTPS for all client-server communication. The system shall store [.changed]#GymGoer# credentials only using secure, non-reversible hashing managed by the authentication provider (Supabase Auth).

Requirements for additional at-rest encryption beyond managed provider defaults will be researched using Supabase documentation and project risk assessment.

====== Operational Observability (Maintainability/Operability)

The system shall provide means to detect and diagnose failures by recording, at minimum, timestamped error events for:

* failed authentication attempts,
* failed reads/writes to persistent storage,
* unhandled application errors affecting core features.

The specific logging retention period and monitoring strategy will be defined after the team selects deployment and monitoring tooling.

===== Notes on Measurement and Validation

* “Normal load” refers to typical course-expected usage patterns and will be approximated during testing with scripted actions matching Concurrent Usage Target.
* Any undetermined values will be finalized by (1) reviewing Supabase platform constraints, and (2) running basic load tests to determine attainable thresholds without conflicting with other requirements.
