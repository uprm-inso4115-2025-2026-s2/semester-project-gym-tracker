==== 2.2.4 Interface Requirements
===== Definition

In this project, _interface requirements_ #describe how users interact with the system to input, modify and view information related to their fitness activities. These focus on the boundary between the user and the system, specifying the actions users can perform and the information presented in response.#

#Interface requirements define the available user interactions without specifying implementation details or internal data structures.#

===== Interface Requirements

====== User Initialization

The system shall provide means for a real-world individual to create a user account #by entering required registration information#.

====== Recording Real-World Workouts

#The system shall provide an interface for a user to record a workout session that occurred in the real world.#

====== Editing and Correction of Workout Data

The system shall provide means for a user to #view and# edit previously recorded Workout Sessions in order to correct incorrect or incomplete entries.

#Satisfiability and Feasibility Discussion#
#Satisfiability:# This requirement is satisfiable within the current design because the interface section already defines workflows in which a gym goer reopens a previously recorded Workout Session, edits incorrect information, submits the correction, and triggers recalculation of dependent indicators. The interaction requirements also now specify validation on submit and resilience behavior for backend persistence failures, which means correction is not treated as an informal idea but as a supported interaction path with defined system behavior.#

#Feasibility:# This requirement is feasible within project constraints because editing previously stored records is a common web-application interaction supported by the selected React + Supabase stack. The implementation complexity is moderate rather than exceptional: the system must retrieve the existing record, allow authorized modification, validate the updated values, persist the correction, and refresh derived indicators. Those steps fit the current project architecture and do not require specialized external systems beyond the backend and interface mechanisms already documented.#

====== Goal Initialization and Update

The system shall provide means for a user to #create, view# and update fitness Goals.

====== Viewing Progress and History
#The system shall provide means for a user to view their recorded workout history and overall progress over time.#

====== Automatic Streak Synchronization

#The system shall display the user’s current streak or consistency indicator.The system shall update the displayed streak or consistency indicator in response to changes in workout data.#

#Validation Strategy#
#For key interaction flows involving workout entry or editing, the interface shall apply batch validation on submit before persistence. Required fields shall be checked when the user attempts to save, and the system shall reject the submission if required information is missing or invalid. Validation feedback shall identify the affected fields clearly enough that the user can correct the entry immediately.#

#The validation strategy for Workout Session entry shall, at minimum, reject:#
#* missing required fields,#
#* workout dates in the future, and#
#* malformed or contradictory values that violate defined data validation rules.#

#Resilience Behavior for Backend Failures#
#For key interaction flows that persist or modify Workout Sessions, the interface shall not present the operation as successful until the backend confirms persistence. If a backend write fails, the system shall present explicit failure feedback to the user and shall retain the entered data locally long enough to support immediate retry or correction rather than forcing complete re-entry.#

#If the failure is caused by a transient connectivity or service issue, the interface shall allow the user to retry submission. If local retention is used while the write remains unconfirmed, the interface shall make clear that the Workout Session is not yet part of the persistent Workout History. Once persistence succeeds, dependent indicators such as Streak, Consistency, and Weekly Summary data shall be refreshed from the stored Workout History.#

#Preconditions and Assumptions for Key Interaction Flows#
#Unless explicitly stated otherwise, the key interaction flows below assume that the gym goer is authenticated, has an active session, and is interacting with their own account data. Flows that create or edit Workout Sessions also assume that the user has reached the relevant page or form and that the client can attempt communication with backend services, even if that attempt later fails.#

====== Example Usage Scenario

#Scenario 1: Late Logging and Editing a Past Entry#

#Alejandro finished a gym workout on Monday evening after classes. He got home tired, ate dinner, and forgot to record the session immediately.Later that night, he remembered that he wanted to keep his weekly history accurate, so he opened the web application, logged into his account, and navigated to the workout recording page. He selected Monday as the workout date, chose "gym" as the workout type, entered the session duration, and saved the entry. Upon submission, the system created a persistent internal representation of that Workout Session under Alejandro's account and recalculated progress and streak values derived from the updated workout history.#

#The next morning, Alejandro realized that he had entered the wrong
duration because he forgot to include his cooldown. He reopened the application, navigated to his most recent recorded session, selected the edit option, corrected the duration, and saved the change. The system updated the stored Workout Session, preserved its association with the same user, and recalculated the dependent indicators so that the internal representation remained consistent with Alejandro's real-world activity.#

#Scenario 2: Missed Day and Recovery After a Broken Streak#

#Ana had recorded workouts on Monday, Tuesday, and Wednesday and had been paying close attention to her weekly consistency. On Thursday, she stayed late finishing coursework and did not work out. When she opened the
application on Friday afternoon to review her progress, she saw that her previous streak had ended because a full expected day had passed without a recorded workout. However, the rest of her weekly activity history was still visible, so the missed day did not erase the effort she had already made earlier in the week.#

#That evening, Ana decided to restart instead of giving up on the week. She went to the gym, returned home, opened the application, and recorded a new Workout Session with the correct date and workout type. The system stored the entry, updated her weekly progress indicators, and reflected that even though the old streak had been broken, the week still contained meaningful activity. This scenario validates recovery after a non-happy-path event rather than only ideal uninterrupted use.#

#Scenario 3: Invalid Input Rejected Before Persistence#

#Derek went for a run on Sunday morning and wanted to log it quickly before starting the rest of his day. While filling out the form, he accidentally selected a workout date in the future and left one of the required fields empty. He submitted the entry anyway. The system rejected the submission before persistence and displayed validation feedback indicating that workout dates cannot be in the future and required fields cannot be empty.No Workout Session was stored.#

#Derek corrected the date, completed the required information, and
submitted the form again. This time, the system accepted the data,
persisted the Workout Session under Derek's account, and updated his history accordingly. This scenario validates that invalid interface input is blocked before storage and that the user can recover immediately by correcting the entry.#

#When Alejandro selects Save, the system performs batch validation on submit before persistence. Required fields must be present, the workout date must not be in the future, and the entry must satisfy the applicable data validation rules. If validation fails, the system rejects the submission and shows correction-oriented feedback without persisting the Workout Session.#

#Successful persistence behavior:#
#If validation succeeds and the backend confirms persistence, the system creates a persistent internal representation of that Workout Session under Alejandro’s account and recalculates progress and Streak-related values derived from the updated Workout History.#

#The next morning, Alejandro realized that he had entered the wrong duration because he forgot to include his cooldown. He reopened the application, navigated to his most recent recorded session, selected the edit option, corrected the duration, and saved the change. The system updated the stored Workout Session, preserved its association with the same user, and recalculated the dependent indicators so that the internal representation remained consistent with Alejandro's real-world activity.#

#Edit validation behavior:#
#When Alejandro saves the correction, the system again performs batch validation on submit before applying the update. If the edited data is invalid, the update is rejected and the original stored Workout Session remains unchanged.#

#Resilience behavior for backend failure:#
#If the backend fails while creating or updating the Workout Session, the system shall not report success. It shall display explicit failure feedback and retain Alejandro’s entered values locally long enough to support immediate retry or correction. Until backend confirmation is received, the session is not treated as part of the persistent Workout History and dependent indicators are not finalized from it.#

#If the retry succeeds, the system updates the stored Workout Session, preserves its association with the same user, and recalculates dependent indicators so that the persistent representation remains consistent with Alejandro’s real-world activity.#
