=== 4.3 Domain and Requirements Acquisition

This section documents a concrete plan for how we will continue acquiring domain knowledge and requirements beyond the initial brainstorming and informal stakeholder discussions already described in Section 1.4. The guideline explicitly asks for specificity and named resources, not generic statements. 

==== 4.3.1 Acquisition Plan

We will acquire additional domain and requirement information using four complementary streams:

1. *Targeted stakeholder micro-interviews (15–20 minutes each)*  
   We will interview at least:
   - 5 beginner gym-goers (aligning with Alejandro-type constraints),
   - 3 mixed routine users (run + gym, Derek-type),
   - 3 habit-focused users (Ana-type, sensitive to tone/reminders).
   Each interview will be scenario-based (e.g., “log a workout in under 30 seconds”, “weekly goal summary interpretation”) to validate and refine requirements.

2. *Structured survey (quantitative check)*  
   A short survey distributed to UPRM peers to measure:
   - common tracking fragmentation patterns,
   - biggest friction sources (time, complexity, forgetting),
   - desired summary frequency (daily vs weekly),
   - reminder preferences (frequency/tone).

3. *Competitive feature review (existing apps)*  
   We will analyze 3–5 popular tracking apps to extract:
   - minimum viable logging fields,
   - streak/consistency presentation patterns,
   - weekly summary formats,
   - where feature overload increases friction.

4. *Low-fidelity prototype walkthroughs*  
   Once basic screens exist, we will run short “think-aloud” sessions to discover missing requirements at the interface boundary (what users expect to edit, undo, confirm, or see immediately).

==== 4.3.2 Resources and Why We Use Them

We will use diverse resources, as recommended by the guideline: stakeholders + “literature-like” sources + artifact review. 

Primary resources:
- Direct stakeholders: UPRM students, beginner/intermediate gym users, casual runners.
- Existing tools: fitness tracking apps (to identify friction patterns and common mental models).
- Internal artifacts already produced: A3 problem background and countermeasures (to keep alignment with the project’s original problem framing).

==== 4.3.3 Incorporating New Findings

When new findings affect the domain model or requirements:
- We update terminology and domain narrative if a new concept becomes central.
- We revise epics/user stories if stakeholder goals shift.
- We update domain/interface/machine requirements, and record the reason for change in the logbook and linked GitHub issues.
- We update traceability links (Section 4.4) so changes can be followed from new evidence → updated requirements → updated tests/tasks.

==== Workout Data Validation and Integrity
:author: Héctor L. Rivera Betances

== 1. Introduction

Workout tracking apps depend a lot on the data users enter, such as weight, reps, sets, and exercise type. If this data isn’t properly validated, it can become inconsistent or incorrect, which affects features like progress tracking and performance analysis. That’s why data validation is important—it helps keep the information logical and reliable.

== 2. Importance of Data Integrity

Data integrity is essential in fitness apps because training decisions are often based on this information. If users enter incorrect values, like negative weights or zero reps, the system can produce misleading results. Keeping data accurate builds user trust, improves analysis, and helps prevent system errors.

== 3. Common Data Validation Issues

Some common problems include negative or zero values, missing fields, wrong data types, or unrealistic numbers. For example, entering an extremely high weight or using an invalid format can break calculations like training volume or progress tracking.

== 4. Validation Strategies

Validation can happen at different levels. Frontend validation gives users immediate feedback, while backend validation ensures the data is correct no matter how it’s submitted. Using both together makes the system more reliable.

== 5. Technical Considerations

From a technical perspective, it’s important to define clear and reusable validation rules. For example, functions can check that weight, reps, and sets are greater than zero. Database constraints and proper data types also help maintain data integrity.

== 6. Example Validation Logic

A good validation system checks that each workout entry meets basic requirements before being stored. This includes making sure numeric values are positive and that all required fields are filled.

== 7. Benefits and Limitations

The main benefit is more accurate and reliable data. However, if validation rules are too strict, they might limit flexibility for advanced users. It’s important to find a balance between control and usability.

== 8. Conclusion

Validating workout data is essential for building a reliable and scalable fitness app. By ensuring consistency and accuracy, the system can provide meaningful insights and support long-term progress.
