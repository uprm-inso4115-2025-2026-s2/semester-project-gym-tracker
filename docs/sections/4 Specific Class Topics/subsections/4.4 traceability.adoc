=== 4.4 Traceability

The purpose of traceability is to set up deliverables so we can answer impact questions (e.g., “if requirement X changes, which goals/personas/tests are affected?”). This section defines the tagging/linking scheme we will use across needs, goals, epics, requirements, and verification.

==== 4.4.1 Traceability Codes

We will label artifacts with short IDs and reference them inline:

- Needs: N1, N2, ... (from Section 1.2.2)
- Derived goals: G1, G2, ... (from Section 1.5)
- Epics: E1..E5 (from Section 2.2.1)
- Domain requirements: DR1, DR2, ... (from Section 2.2.3)
- Interface requirements: IR1, IR2, ... (from Section 2.2.4)
- Machine requirements: MR1, MR2, ... (from Section 2.2.5)
- [.added]#Acquisition artifacts/evidence: AQ1, AQ2, ... (from Section 4.3 questionnaires, interviews, and source reviews)#
- [.added]#Elicitation findings/resolution items: FE1..FEn, RT1..RTn (from Section 2.2.3 inconsistency cases and resolutions)#
- [.added]#Design decisions: DD1, DD2, ... (domain modeling, interface behavior, architecture, and persistence decisions documented in Sections 2.1, 2.2, 2.3, and 4.3)#
- [.added]#Implementation components: IC1, IC2, ... (source files, UI components, API modules, and utility modules that realize requirements)#
- [.added]#Test cases: TC1, TC2, ... (unit, integration, and acceptance tests that verify requirements or implementation behavior)#
- Verification checks/tests: V1, V2, ... (from Section 3.2)
- GitHub issues/tasks: GH-## (issue number)

==== 4.4.4 How We Will Maintain Traceability

- Each requirement section will include a short “Supports: {G*, N*, Persona}” line.
- [.added]#Each acquisition artifact in Section 4.3 will keep its own ID (for example AQ1) so later changes can reference the evidence source separately from the elicitation decision derived from it.#
- Each verification item (Section 3.2) will reference the requirement IDs it verifies.
- Each GitHub issue will include the relevant IDs in its description (e.g., "DR3, G2, N1") so work items remain traceable to stakeholder value.
- [.added]#Each implementation pull request or issue comment that changes requirement-relevant behavior must list the affected requirement IDs, design decisions, implementation components, and test cases.#
- [.added]#When a requirement, design decision, source file, or test is removed, its traceability entry is not silently deleted. The row is updated with a disposition such as replaced by, merged into, deferred, or obsolete, so the history of the change remains inspectable.#

This scheme supports quick impact analysis when requirements evolve during later milestones.

==== [.added]#4.4.5 Traceability Policy#

[.added]#This subsection defines the traceability policy for the GymTracker project: what should be traceable, what should not, at what level of granularity, what alternatives were considered, and why this approach was chosen.#

===== [.added]#What should be traceable#

[.added]#The following artifact relationships are required to be traceable in this project:#

* [.added]#Stakeholder needs (N*) to derived project goals (G*)#
* [.added]#Goals (G*) to epics (E*) and from epics to domain requirements (DR*), interface requirements (IR*), and machine requirements (MR*)#
* [.added]#Acquisition artifacts (AQ*) to the requirements they informed and the elicitation decisions (FE*, RT*) they produced#
* [.added]#Requirements to design decisions (DD*) that explain why the selected domain model, interface behavior, persistence behavior, or architecture satisfies the requirement#
* [.added]#Domain requirements and interface requirements to the implementation components (IC*) that realize them, identified by source file or documented implementation fragment#
* [.added]#Requirements to the verification checks or acceptance tests (TC*, V*, test file + test name) that confirm them#
* [.added]#GitHub issues (GH-##) to the requirements they address, so task work remains linked to stakeholder value#

===== [.added]#Traceability link types#

[.added]#The following link types are used in the traceability matrix and in GitHub/Jira issue descriptions. Each link is bidirectional: if a requirement references a design decision, the design decision entry must also reference the requirement it supports.#

[cols="1,2,4", options="header"]
|===
|[.added]#Link type# |[.added]#Direction# |[.added]#Meaning#

|[.added]#satisfies#
|[.added]#DD* -> DR*/IR*/MR*#
|[.added]#A design decision provides the modeling, interface, or architectural choice that fulfills a requirement.#

|[.added]#realizes#
|[.added]#IC* -> DR*/IR*/MR*#
|[.added]#A source file, component, or implementation fragment provides executable behavior required by the requirement.#

|[.added]#verifies#
|[.added]#TC*/V* -> DR*/IR*/MR* or IC*#
|[.added]#A test case, checklist item, or verification result confirms the requirement or component behavior.#

|[.added]#derives from#
|[.added]#DR*/IR*/MR* -> N*/G*/AQ*/FE*/RT*#
|[.added]#A requirement is justified by a stakeholder need, goal, acquisition artifact, or elicitation decision.#

|[.added]#impacts#
|[.added]#Change request/GH/Jira issue -> traced artifacts#
|[.added]#A proposed change is expected to require review or modification of the linked requirements, design decisions, source files, tests, or documentation sections.#

|[.added]#supersedes#
|[.added]#New artifact -> old artifact#
|[.added]#A requirement, design decision, component, or test replaces an older artifact while preserving the historical trace.#
|===

===== [.added]#What should NOT be traced at this level#

[.added]#The following are explicitly excluded from this traceability scheme to keep maintenance effort proportionate:#

* [.added]#Inline source code comments pointing to requirement IDs — rejected because they become stale on refactoring and create a false sense of completeness#
* [.added]#CSS and styling decisions — these are presentation choices that do not correspond to domain requirements or stakeholder needs#
* [.changed]#Third-party library selection (Supabase, React, Vite) — implementation choices traceable to machine requirements at most, not to domain requirements or GymGoer stories#
* [.added]#Build configuration and CI pipeline details — infrastructure, not domain behavior#
* [.added]#Internal refactors where no behavior visible to a GymGoer changes#

===== [.added]#Granularity#

[.added]#Traceability is maintained at the *requirement level*, not at the sub-clause level. A link from N2 to "Low-Effort Logging" is sufficient; the link does not need to reference individual bullet points within the requirement. Design traceability is maintained at the named decision level (DD*) instead of at every paragraph that discusses a decision. Implementation traceability is maintained at the feature/component/source-file level (IC*), for example `LogWorkoutModal.tsx` realizes "Recording Real-World Workouts"; line-level traceability is not required. Verification traceability is maintained at the test file and test name level (TC*) or at the inspection/verification item level (V*).#

===== [.added]#When links are created and maintained#

[.added]#Traceability links are created at four points in the lifecycle. During requirements work, the requirement owner links each DR*/IR*/MR* item back to at least one N*, G*, AQ*, FE*, or RT* source. During design work, the documentation owner records the DD* decision that satisfies or constrains the requirement. During implementation, the developer links the requirement and design decision to the IC* source file or implementation fragment in the GitHub/Jira issue. During verification, the tester links each TC* or V* item to the requirement and implementation component being checked.#

[.added]#Links are maintained whenever one of the linked artifacts changes. A pull request or issue that changes a requirement-relevant behavior must update Section 4.4, the affected requirement text, and the relevant verification summary in Section 3.2 before the issue is considered closed.#

===== [.added]#Alternatives considered#

[cols="1,3,2", options="header"]
|===
|[.added]#Alternative# |[.added]#Description# |[.added]#Reason for rejection#

|[.added]#Issue-only traceability#
|[.added]#Track only GitHub issue → requirement. No need-to-goal or requirement-to-test links.#
|[.added]#Too shallow. Does not support impact analysis when a stakeholder need changes, because the need-to-requirement path is missing.#

|[.added]#Fine-grained sub-requirement traceability#
|[.added]#Decompose each requirement into sub-clauses and trace each individually.#
|[.added]#Too high maintenance for a course project. Sub-clause IDs go stale on every requirement edit.#

|[.added]#Code-level traceability (inline comments)#
|[.added]#Embed requirement IDs in source code comments at the function level.#
|[.added]#Brittle. Silently breaks on refactoring. Creates a misleading audit trail.#

|[.added]#Tool-assisted traceability (dedicated traceability tool)#
|[.added]#Use a requirements management tool (e.g., JIRA, Doorstop) to maintain a live traceability graph.#
|[.added]#Not available within the course tooling. GitHub Issues approximate this at reduced fidelity.#
|===

===== [.added]#Why this approach was chosen#

[.added]#Requirement-level traceability with stable IDs (N*, G*, E*, DR*, IR*, MR*) balances impact-analysis capability against maintenance cost. When a requirement changes, the ID stays the same and the links to needs, goals, and tests remain valid even if the text is rewritten. This is the minimum granularity needed to answer the core impact question: "if we change requirement X, what else must change?" The GitHub issue linkage adds a lightweight development workflow integration that does not require an external tool.#

==== [.added]#4.4.9 Effort Assessment for Traceability Maintenance#

[.added]#This subsection assesses the effort required to maintain traceability information through each of the three change scenarios above, and draws a general conclusion about the cost-benefit relationship of the chosen traceability scheme.#

[cols="1,2,2,2", options="header"]
|===
|[.added]#Scenario# |[.added]#Implementation effort (estimated)# |[.added]#Traceability maintenance effort (estimated)# |[.added]#Key traceability value delivered#

|[.added]#Scenario 1 (grace period removed)#
|[.added]#2–4 hours: modify `streakcalc.ts`, update test suite, verify build#
|[.added]#~1 hour: update DR text, remove WI-3, update state machine diagram, update Section 3.2 summary#
|[.added]#Prevented a stale weak inconsistency entry (WI-3) and a stale diagram from persisting after the change#

|[.added]#Scenario 2 (goal counting semantics)#
|[.added]#4–6 hours: modify `workouts.ts`, update two feedback components, update tests#
|[.added]#~2 hours: update DR text, revisit AQ1-Q3 evidence, update implementation fragment in 2.3.1, update Section 3.2#
|[.added]#Identified that AQ1-Q3 acquisition evidence conflicts with the proposed change — traceability surfaced a stakeholder alignment risk that would otherwise have been missed#

|[.added]#Scenario 3 (Google-only auth)#
|[.added]#6–10 hours: remove 3 pages, simplify LoginPage, update acceptance tests, configure Supabase#

[.added]#*General conclusion:* Across all three scenarios, maintaining the traceability information added between 1 and 3 hours of documentation overhead per change, compared to an implementation effort of 2 to 10 hours. The overhead ratio is approximately 20–30% of implementation time. The primary value of the scheme was not in the matrix itself but in the structured question it forces: "which requirements, tests, and documentation sections reference the artifact being changed?" In two of the three scenarios (Scenario 2 and Scenario 3), traceability surfaced a non-obvious artifact that would likely have been missed without it: an acquisition evidence conflict in Scenario 2 and a stale implementation fragment in Scenario 3.#

==== [.added]#4.4.10 Traceability Maintenance Plan#

[.added]#The traceability matrix is maintained as part of normal development, not as a separate end-of-milestone cleanup task. The team uses this documentation section as the version-controlled source of truth and mirrors the same IDs in GitHub/Jira work items when those tools are used.#

[cols="1,2,4", options="header"]
|===
|[.added]#Role# |[.added]#Responsible member / group# |[.added]#Responsibility#

|[.added]#Traceability owner#
|[.added]#Documentation Team Leader / assigned issue owner#
|[.added]#Keeps Section 4.4 current, verifies that new requirements have source needs and design/code/test links, and checks that closed issues updated the matrix.#

|[.added]#Requirement owner#
|[.added]#Member editing Section 2.2 requirement text#
|[.added]#Adds or updates N*, G*, AQ*, FE*, and RT* links when requirement wording changes.#

|[.added]#Developer#
|[.added]#Member implementing the issue#
|[.added]#Lists affected IC* implementation components, includes requirement IDs in the GitHub/Jira issue, and updates implementation documentation when behavior changes.#

|[.added]#Tester / reviewer#
|[.added]#Member responsible for verification or PR review#
|[.added]#Confirms that each changed requirement has at least one TC* or V* verification link and that old tests are updated or marked obsolete.#
|===

[.added]#Maintenance procedure:#

* [.added]#At issue creation, the owner adds the affected N*, G*, DR*/IR*/MR*, DD*, IC*, and TC* IDs when they are known. Unknown links are marked `TBD` and resolved before closing the issue.#
* [.added]#During implementation, any discovered new dependency is added to the issue and to the matrix before the pull request is reviewed.#
* [.added]#During review, the reviewer checks whether requirement text, design rationale, implementation references, tests, and logbook entries agree.#
* [.added]#At milestone closure, the documentation lead performs one traceability review pass over Section 4.4, Section 3.2, and Section 2.3 to identify stale file names, obsolete tests, and missing reverse links.#

[.added]#Review frequency: traceability is reviewed once per high-urgency issue, once before each milestone submission, and whenever a requirement or interface behavior is changed after implementation has already started.#
